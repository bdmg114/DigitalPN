# 데이터 형식과 전송

## 1. 레코드: 한 줄 = 항목의 한 리비전

저장과 전송은 같은 형식을 쓴다. UTF-8 JSON 객체 하나가 한 줄이다(JSONL).
정식 정의는 [`schema/item.schema.json`](../schema/item.schema.json), 예시는 [`schema/examples/sample.jsonl`](../schema/examples/sample.jsonl).

```json
{"v":1,"seq":42,"id":"01M73Z7P18V37E3S3E28JT97KB","note":"01M73Z7D80M9S346Q3D25VT4F5","ord":2048,"kind":"text","text":"키 간격은 9mm로 시작하고 시제품에서 오타율을 재서 조정한다. #하드웨어","tags":["하드웨어"],"rev":1,"created":"2026-11-11T09:13:29+09:00","updated":"2026-11-11T09:13:29+09:00","clock":"synced","dev":"dpn-7f3a2c"}
```

| 필드 | 설명 |
|---|---|
| `v` | 스키마 버전 (1) |
| `seq` | 기기 저널 일련번호. 기기 안에서 단조 증가. 전송 커서로 쓴다. |
| `id` | 항목 ID (ULID). 수정·삭제해도 유지된다. |
| `note` | 속한 메모의 ID. 메모의 첫 항목 `id`와 같다. |
| `ord` | 메모 안 순서. 1024 간격으로 매겨 사이에 끼워 넣을 수 있다. |
| `kind` | `text` 문단 / `task` 할 일 / `head` 제목 |
| `text` | 본문 |
| `done` | `task`일 때 완료 여부 |
| `tags` | 본문의 `#태그` (선택) |
| `rev` | 리비전. 같은 `id`에서는 큰 쪽이 최신이다. |
| `deleted` | `true`면 삭제 표시 (선택) |
| `created`, `updated` | RFC 3339 시각 |
| `clock` | `unsynced`면 시계가 맞지 않은 상태에서 쓴 것. 순서는 `seq`를 믿는다. |
| `dev` | 기기 ID |

### AI에 넘기기 좋게 한 점

- **항목이 독립적이다.** 한 줄만 떼어 놓아도 어느 메모의 몇 번째인지, 언제 썼는지, 종류가 무엇인지 알 수 있다. 그대로 검색·임베딩 단위로 쓴다.
- **구조가 평평하다.** 중첩이 없고 필드 이름이 뜻 그대로다. 긴 문서를 통째로 넘기지 않고 필요한 줄만 고를 수 있다.
- **메모는 저장하지 않고 유도한다.** `note`가 같은 항목을 `ord` 순으로 모으면 메모다. 메모 단위 요약이 필요하면 받는 쪽에서 묶는다.
- **이력이 남는다.** 수정은 덮어쓰지 않고 새 줄로 쌓인다. 최신 상태만 필요하면 `id`별로 `rev`가 가장 큰 줄을 고르고 `deleted`인 것을 뺀다.

최신 상태를 얻는 규칙:

```python
latest = {}
for line in lines:
    r = json.loads(line)
    if r["id"] not in latest or r["rev"] > latest[r["id"]]["rev"]:
        latest[r["id"]] = r
items = sorted((r for r in latest.values() if not r.get("deleted")),
               key=lambda r: (r["note"], r["ord"]))
```

## 2. 전송 모델

기기는 **보내기만 하는 추가 전용 로그**다. 받는 쪽은 "어디까지 받았다(`seq`)"만 알려 주면 된다.

```
받는 쪽                        기기
   │── pull {after: 40} ────────▶│
   │◀──── 레코드 seq 41…46 ──────│
   │◀──── end {head: 46} ────────│
   │── ack {seq: 46} ───────────▶│   기기는 이 대상의 커서를 46으로 저장
```

- 커서는 전송 대상별로 따로 둔다(앱, 서버, …).
- 중간에 끊기면 `ack`하지 않은 지점부터 다시 받는다. 같은 줄을 두 번 받아도 `(id, rev)`가 같으면 버리면 되므로 중복이 생기지 않는다.
- 세 전송 경로가 같은 제어 메시지와 같은 레코드를 쓴다.

제어 메시지 (JSON 한 줄):

| 방향 | 메시지 | 뜻 |
|---|---|---|
| → 기기 | `{"op":"hello","time":"2026-11-11T09:20:00+09:00"}` | 시각 맞추기. 응답으로 기기 정보 |
| ← 기기 | `{"op":"info","dev":"dpn-7f3a2c","fw":"0.1.0","proto":1,"head":46,"cursor":40}` | `head`: 최신 seq, `cursor`: 이 대상이 마지막으로 ack한 seq |
| → 기기 | `{"op":"pull","after":40,"limit":200}` | `after`보다 큰 레코드 요청 |
| ← 기기 | 레코드 줄들, 이어서 `{"op":"end","head":46}` | |
| → 기기 | `{"op":"ack","seq":46}` | 여기까지 안전하게 저장했음 |
| → 기기 | `{"op":"config.get"}` / `{"op":"config.set","patch":{…}}` | 설정 읽기·쓰기 (비밀 값은 쓰기만 가능) |

## 3. 블루투스 (BLE → 앱)

- 연결 보안: LE Secure Connections. 처음 연결할 때 기기 화면에 6자리 숫자를 띄우고 앱에서 입력한다. 이후에는 본딩된 기기만 접속할 수 있다.
- 광고는 전송 상태에 들어갔을 때만 한다.

GATT 서비스 `6349bcb0-16bb-4df4-ba76-d693772edec1`

| 특성 | UUID 끝자리 | 속성 | 내용 |
|---|---|---|---|
| control | `…bcb1…` | write | 제어 메시지 (→ 기기) |
| stream | `…bcb2…` | notify | 기기가 보내는 줄 (제어 응답과 레코드) |

조각내기: 알림 하나의 첫 바이트가 플래그(`0x01` = 줄의 마지막 조각), 나머지가 UTF-8 조각이다. 받는 쪽은 마지막 조각이 올 때까지 이어 붙인다. MTU는 247을 요청한다. 흐름 제어는 `pull`의 `limit`으로 한다(받은 만큼 `ack`하고 다음 `pull`).

앱은 받은 줄을 그대로 파일·DB에 넣으면 된다. Web Bluetooth로도 구현할 수 있어 설치 없는 웹 페이지 수신기가 가능하다.

## 4. 인터넷 (Wi-Fi → 서버)

기기가 전송 상태에서 Wi-Fi에 붙어 직접 올린다. 서버는 엔드포인트 두 개만 구현하면 된다.

```
GET  {url}/cursor
     Authorization: Bearer <기기 토큰>
  → 200 {"seq": 40}

POST {url}/items
     Authorization: Bearer <기기 토큰>
     Content-Type: application/x-ndjson
     (본문: 레코드 줄들, 한 번에 최대 200줄)
  → 200 {"seq": 46}        서버가 저장을 마친 마지막 seq
```

- TLS 필수. 인증은 기기별 토큰이며 서버는 토큰에서 `dev`를 확인한다.
- 서버는 `(dev, id, rev)`를 키로 저장해 재전송을 무해하게 만든다.
- 200이 아니면 기기는 커서를 올리지 않고 다음 전송 때 다시 보낸다.
- 시각은 응답의 `Date` 헤더로 맞춘다.

이 규약은 단순해서 자체 서버, 서버리스 함수, 웹훅 수신기 어디에나 올릴 수 있다.

## 5. USB

- **드라이브 모드**: PC에 꽂으면 읽기 전용 드라이브로 보이고 `/j/*.jsonl`을 그대로 복사할 수 있다. 앱도 네트워크도 필요 없다. 드라이브로 연결된 동안에는 기기에서 편집할 수 없다.
- **직렬 모드**: USB 직렬 포트로 2절의 제어 메시지를 줄 단위로 주고받는다. 스크립트로 자동 수집할 때 쓴다.

## 6. 범위 밖

- 받는 쪽에서 고친 내용을 기기로 되돌려 보내는 양방향 동기화는 v1에서 하지 않는다. 기기는 쓰는 도구이고, 정리는 받은 쪽에서 한다.
- 기기 저장소 암호화는 v1에 없다. 분실에 대비하려면 ESP32의 플래시 암호화를 켜는 것을 2단계에서 검토한다.
